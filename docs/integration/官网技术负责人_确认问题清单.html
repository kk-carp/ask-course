沟通口径（建议开场即说明，可显著降低对方防御心理）
需要的是一处部署层的注入授权与一个排期窗口，不是索取整套前端源码。做法等同于第三方客服系统的接入方式，脚本可随时摘除。同时请对方知悉：Agent 带来的高意向线索会按课程交付给对应售前，不改变现有业绩归属规则（归属最近一次人工接触的售前）。
可直接使用的开场："我们想给官网加一个售前咨询助手，帮学员选课、并把有意向的人按课程交给对应的售前。不带任何官网改造要求——只想知道能不能在部署层挂一段可摘除的脚本，以及几处数据口径。业绩归属现在怎么算，之后还是怎么算。"

组一 · 接入授权与上线路径 决定"能不能接上" · 两个阻塞项（B2 / B5）集中在本组

我方已完成的实测（B3 的现状答案，不必再请对方重复核查）
对 www.arborseek.com 首页发起真实请求：响应头为 Server: nginx，未出现 Content-Security-Policy，亦未出现 X-Frame-Options；页面仅挂一个主 JS 产物与百度统计，未部署任何标签管理器。由此得到两个可直接使用的结论：其一，当前注入不会被 CSP 拦截，原设想的"策略拦截"并非现实障碍，本条只剩"后续是否有启用计划、能否为来源预留白名单"需要对方确认；其二，因官网未安装标签管理器，"改用标签管理器注入"这条不碰官网代码的替代通道暂时走不通，可在会上作为备选方案提出（行业内有成熟先例）。
编号要问什么为什么关键期望结论若不可用的降级方案
B2 能否提供部署层的一处脚本注入权限？
① 官网的部署方式是什么（Nginx / CDN / 前端构建流水线）？
② 由谁来操作这一段？
③ 能否支持版本号 + 远程开关，出问题可即时停用、随时摘除？		 这是不用源码也能挂载悬浮球的标准做法（第三方客服系统即如此）。决定能否走上线路径，是本项目唯一的技术阻塞点。 可 / 否 + 操作方 + 是否支持灰度与快速摘除 改用跨域 iframe 嵌入。但会失去同域读登录态与读当前路由的能力，R9 登录态保持、R10 课程上下文识别难度显著上升，且需官网配合调整页面。
B3 站点后续是否有启用 Content-Security-Policy 的计划？（现状我方已实测：响应头中未包含 CSP，当前注入不会被拦截——本条只需确认未来）
① 安全侧是否有启用 CSP 的路线图或时间点？
② 若启用，能否为本项目预留白名单——script-src（脚本来源）、connect-src（接口与 SSE）、frame-src（若走 iframe 备选）？		 当前不构成障碍，但站点一旦启用严格 CSP 而未放行，已上线的悬浮球会被浏览器整体拦截，属"上线之后才暴露"的故障；同时 Agent 需调用自有接口与流式通道，受 connect-src 约束。提前预留白名单，成本近乎为零；事后补救则需重走安全流程。 是否有启用计划 + 若启用可否预留三类来源白名单（脚本 / 接口 / 流式） 若对方将启用严格 CSP 且不接受放行：改为 iframe 方案（frame-src 仍需放行）；或并入官网源码集成分支，排期随即进入官网迭代节奏。
B4 向生产环境注入第三方脚本需经过哪些安全与合规评审？
周期多长？责任人是谁？需要我方提前提供哪些材料（安全说明 / 数据处理说明等）？		 这是真实存在的流程阻力，且由对方主导。提前摸清可避免开发完成后卡在流程上。 流程清单、周期、责任人、所需材料 无替代路径。评审未通过只能走源码集成分支，上线时间并入官网迭代排期。
B5 这件事在你们内部迭代中能排到什么优先级与时间窗？
能否先做"低风险版"——只挂一个静态悬浮球、暂不接任何接口——用于验证效果？		 脚本注入属官网团队本职工作之外的需求，不明确排期就容易被主线需求长期挤占，项目会停在"方案完整但上不了线"。 可给出大致时间窗，或明确"本期无法排入" 先行 P0 独立部署：只做「知识库问答 + 未命中转人工」，优先服务售前内部，不碰官网、不需授权，同时积累语料与评测基线。

组二 · 售前码与内容数据 决定推荐与转人工的正确性

编号要问什么为什么关键期望结论若不可用的降级方案
B1 售前二维码字段 pre_sale_service_qrcode 的配置方式
① 是否按课程独立配置？实测样本与 tutor.qrcode 指向同一张图，是否复用了班主任码？
② 能否在后台维护？课程新增或售前调整时由谁更新？
③ 字段为空时，前端现有的兜底逻辑是什么？		 接口已实测携带该字段，不必另建映射表，本项剩余的是配置口径。但若确实复用了班主任码，则与"班主任属售后通道、不承担售前"的定位冲突，需业务侧先行厘清。这直接影响 R24 的兜底设计与"弹错码"这一高频故障。 配置粒度 + 后台可维护性 + 空值兜底逻辑 改为 Agent 侧维护一份课程—售前映射表。可行，但需专人持续同步，是长期维护成本，且与官网数据存在不一致风险。
B6 配套接口与内容承载方式
① 是否存在章节 / 大纲、讲师详情、常见问题等独立接口？
② 9 个板块内容是否全部以图片承载？
③ 全站约多少门课、每门平均多少张图（用于估算文本化工作量）？		 接口已实测：结构化字段可读，但课程正文与多数板块为图片、无检索文本。而"这门课到底讲什么"是学员最高频的问题。这已属内容准备问题、不是技术缺口，但直接决定知识库覆盖质量与推荐理由的可信度。 配套接口清单 + 图片承载范围 + 数据量估算 Agent 侧做 OCR 批量转换，但准确率需人工抽检；若效果不达标，退为运营逐课补录，周期显著拉长。
B11 登录态的存储与读取方式
① 登录态放在哪里（localStorage / Cookie / Pinia）？
② token 的字段名与有效期？
③ 同域脚本能否直接读取？
④ 未登录用户的判断依据是什么？		 同域注入可直接读登录态，这正是 P1 方案相对跨域 iframe 的核心优势，也是"登录态保持"（R9）能否低成本实现的依据。此处确认清楚，能省掉一次重复登录的转化损耗。 存储位置 + token 字段名 + 有效期 + 未登录判定方式 跨域方案下需官网提供用户信息查询接口，实现难度与排期同步上升。

组三 · 接口数据口径 决定话术与排序的正确性 · 含一处合规风险

编号要问什么为什么关键期望结论若不可用的降级方案
B10 课程接口的数据口径（实测发现四处疑点）
① price_tiers 中"31–60 人 ¥89"高于"1–30 人 ¥69"，单价随人数上升，是否为预期口径？
② price 为数字、original_price 为字符串（"199.00"），类型不一致是否有意？
③ student_count 为 0 而 badge 为 hot，报名人数是否未统计或未对外返回？
④ countdown（阈值 30 天、目标时间为空）实际的业务规则是什么？		 ①②影响价格话术与推荐排序，Agent 一旦把阶梯价讲反，会直接影响成交与信任。③决定社会证明类话术能否使用。
④尤为关键：Agent 若引用倒计时营造紧迫感，必须与实际价格逻辑严格一致，不得虚构截止时间，否则构成虚假促销。		 四项口径逐一确认（特别是倒计时的触发条件与失效规则） 口径明确前，Agent 一律不展示倒计时、不引用报名人数，只展示明确的价格与标签，避免任何可能失真的促销表达。

组四 · 企业微信能力与效果度量 决定成败能否被度量

编号要问什么为什么关键期望结论若不可用的降级方案
B9 企业微信的能力边界
① 是否使用可带来源参数的「联系我」活码？
② 客户联系 API / 应用消息 API 是否对本项目开放？
③ 是否开通会话存档？
④ 后台能否提供分渠道的添加客户数与来源统计？		 售前承接渠道已升级企业微信，但能力是有条件的。若仅完成账号迁移、未启用活码与接口，则线索归因（R19）与上下文推送（R23）需按降级方案实现，售前语料沉淀（R18）也无法通过会话存档获取。四项直接决定三条需求的实现方式，是当前最关键的技术待确认项。 四项能力逐项确认：已启用 / 未启用 / 需申请 R19 → Agent 侧记录来源 + 售前人工回填；R23 → 生成可复制的线索摘要，由售前手动带入沟通；R18 → 依赖人工整理的沟通记录。三者均可用，但准确度与效率下降。
B8 现有"咨询"按钮的历史数据能否提供？
点击量、扫码率、加好友后转化。若官网侧无埋点，企微后台能否给出分渠道的加好友数？		 这是目前唯一可能拿到的近似基线，其他环节全无数据（无 UV / 咨询量 / 留资量 / 成单量）。有它可让指标目标提前数周设定；没有它只能先花 2–4 周采基线。 可提供 / 明确无统计 采用两阶段法：先按来源分层采集基线 2–4 周，再设目标值。注意不分层看"官网转化率"会把人工功劳算到 Agent 头上。

组五 · 前端配合与指标闭环 决定体验完整度与数据能否闭环

编号要问什么为什么关键期望结论若不可用的降级方案
B7 现有"咨询"按钮与弹窗在哪个组件、如何实现？
能否复用为转人工出口？改造由谁做、是否算入官网迭代工作量？		 转人工可直接复用现成组件与现成的课程—售前映射，省掉整个 IM / 客服系统的建设。同时"入口归一"（把咨询按钮与 Agent 合并为一个入口）必须动它，否则两个入口并存会明显损害体验。 组件位置 + 改造方式 + 工作量归属 由 Agent 侧自行实现弹码，但会出现两个入口并存，且需自行维护映射，体验与维护成本双输。
B12 挂载点约定与灰度开关
① 悬浮球挂在哪个位置不会遮挡现有元素？
② 移动端是否需要单独处理？
③ 注入脚本能否带版本号与远程开关？		 影响首次上线的观感与冲突风险，也决定出问题时能否即时停用而不必等官网发版。 挂载位置约定 + 灰度开关方案 无远程开关时，每次变更都需走官网发布流程，回退速度慢，灰度能力受限。
B13 支付完成结果能否回传？
Agent 侧无法感知"是否完成支付"。能否由官网 / 后台回传支付结果事件，或提供订单查询接口？
字段、触发时机，以及能否带上 Agent 会话标识用于归因？		 北极星指标（Agent 引导的成交）完全依赖这一环。拿不到就只有"转人工"这一层数据，无法计算到成交，整个效果评估会停在漏斗中段。 回传方式 / 查询接口 + 字段 + 触发时机 + 能否带会话标识 以"转人工线索数"作为北极星代理指标，成交数据由人工与后台周报对齐，归因由自动化降为周期性核对。

建议议程 35 分钟，先解决阻塞项

  1. 5 分钟 · 背景与目标——一句话讲清：把"扫码"从第一步变成最后一步；不给官网提改造要求，只要一处注入权限与几处数据口径。
  2. 10 分钟 · 接入授权（B2 / B5，B3 顺带）——本场唯一的关键。目标是当场得到"能否注入、能否排期"两个明确答复；B3 因现状已实测，只需问清后续是否有启用 CSP 的计划、能否预留来源白名单。B4 顺带确认流程与责任人。
  3. 8 分钟 · 数据与接口口径（B1 / B10 / B11 / B13）——重点是 B10 的倒计时规则（合规相关），以及 B13 支付结果能否回传。
  4. 5 分钟 · 企业微信能力（B9 / B8）——B9 四项逐项打勾，未开通的标注"需申请"及申请路径。
  5. 5 分钟 · 前端配合（B7 / B6 / B12）——确认咨询弹窗组件能否复用，并约定挂载点。
  6. 2 分钟 · 责任人与下一步——每项未决事项记录责任人，不阻塞其余事项推进。
