一、P0 的边界：只验证一件事

P0 的命题很窄，也很关键：官网自然流量里的常规咨询，能不能由 Agent 在站内直接承接，只把真正需要人的那部分交给售前。

围绕这个命题，P0 的范围与刻意不做的事如下：

分类内容为什么这样切
做 会话入口（游客与登录两种身份）、课程空间检索、命中生成答案、未命中转人工、线索留痕、来源展示、健康与指标 这条链路已经能验证"站内自助解决率"这一核心命题
不做 问诊层（4 轮画像采集）、课程推荐排序、官网前端集成、OCR 识图问答、跨会话记忆、MCP 工具调用 问诊与推荐是 P1 的主体，也是最大的新增开发量；官网集成依赖外部授权与排期

P0 的验收口径

1
未命中一定有出口
任何一次未命中都必须返回一位售前（课程映射 → 关键词 → 兜底码三级路由），不能出现"未命中且无人可接"。
2
未命中不调模型
沿用 FDE 的硬约束：低于阈值直接拒答，不调用对话模型。这是成本护栏，也是"不编造"的技术保证。
3
能按渠道分开统计
会话启动、命中、未命中、转人工、线索五类事件都带 channel 与 course_id，否则无法判断成效来自 Agent 还是人工。

二、复用总览：搬内核，换外壳

本次复用不是"复制一个项目改改"，而是分层裁定——内核层整段搬运，应用层小改造，产品外壳新写。

内核层 · 原样搬

检索、重排、分词、分块、解析、拒答门控、来源防篡改、限流、埋点、请求链路。

结论：与用户、角色、空间体系零耦合。

应用层 · 小改造

配置、建库、数据模型、请求契约、入口装配、主题负责人服务。

改动集中在"空间从三个变成一个"、"用户从强制登录变成可匿名"。

产品外壳 · 新写

游客态签发、未命中转人工路由、线索落库、课程—售前映射种子。

共 3 个新模块，合计约 400 行。

为什么内核能整段搬——一个必须说清楚的技术事实

FDE 的检索 SQL 里，空间过滤是这么写的：
WHERE chunks.space_id = ANY(CAST(:allowed_spaces AS text[]))
它是参数，不是常量。FDE 的 student / company / teaching 三空间只是一份数据约定，不是内核逻辑。
所以 P0 只要传 ["courses"]，检索、重排、门控全都不需要动。

顺带得到的一个工程红利

embed.py 与 rerank.py 对 sentence-transformers 与 torch 的引用是写在函数内部的延迟导入，不在模块顶层。这带来两个直接好处：

  • 内核模块可以在没装 torch 的环境里被导入、被单元测试、被静态检查——本次的自检脚本正是靠这一点才得以执行；
  • 若 P0 暂时不启用重排（RETRIEVE_USE_RERANK=false），可以完全不安装重排依赖，部署包体量大幅下降。

五、三处关键映射：复用而非新建

P0 之所以能一周内跑通，靠的是 FDE 里已经存在结构完全对应的零件。这不是巧合——"未命中该找谁"和"这题该问谁"本来就是同一类问题。

映射一：topic_owners 表 ＝ 课程 → 售前映射

FDE 原本用它承载「内部主题 → 负责人联系方式」，仅在员工未命中时查询。字段语义平移即可：

FDE 字段P0 语义
topic_key VARCHAR(64) PK课程 ID（与官网 /course/:courseId 对齐）
topic_name课程名称
keywords（逗号分隔）课程别名，用于问题文本兜底匹配
owner_name售前人员姓名
contact售前企微「联系我」活码链接

匹配算法直接复用：match_owner_for_question() 取命中关键词最长的一条，无匹配时返回 configured=false——宁可不给，也不编造联系方式。

映射二：tickets 表 ＝ 未命中线索

FDE 里它是学员工单（有处理人、可回复、状态机 open → replied）。P0 复用它落线索：谁问了什么、该归哪个售前。

新增的四个字段正是归因所需的最小集合：visitor_id（匿名去重）、course_id（课程维度）、channel（渠道维度）、topic_key（对应售前）。

一处需要说明的口径

FDE 的审计日志刻意不记录问题全文，但会话表与工单表存全文。P0 继续沿用后者承载线索原话——线索价值就在原话。这不构成口径冲突：审计仍是日志，不落表。

映射三：advanced_resources ＝ 课程推荐引擎原型 P1 使用

FDE 的「进阶资料推荐」是一个自研的旁路多步 Agent（未使用 LangGraph），流程为：

薄弱点 → 逐个 topic：搜索 → LLM 判定相关性 → 必要时限次改写查询 → 采用
       → 能力分析 → 成文（始终执行，不因步数耗尽而跳过）

可直接继承的三个机制：

  • 有限步进：步数预算 + 强制预留"成文"步骤，保证兜底产出；
  • 防编造：成文前先生成材料目录，模型引用目录外的条目会被直接丢弃；
  • 失败降级：判定返回非法 JSON 时保留打分最高的前 K 条，不无限重试。

P1 改造方向：输入由「薄弱点」换成「用户需求画像（方向 / 预算 / 基础）」，输出由「推荐文章」换成「2–3 门课程 + 适配理由 + 购买入口」。其 search_course 工具本身就是课程检索，改造成本主要在去掉学伴场景的硬编码与替换输出契约。

六、弃用清单：9 类模块因设计相反而不用

有些模块看起来"能用"，但它们的默认行为与本项目正好相反，强行复用会引入错误的默认值——不复用比复用更省事。

模块弃用原因
domain/membership.py多空间 RBAC，与"只有课程空间"的 P0 设计相反
domain/general_assist.py学员专属兜底，且含教学评测专用的拒答词
domain/companion.py学伴能力裁剪，无对应场景
services/memory_service.py跨会话学习记忆（文件保留，未挂载路由）
services/ocr_service.py 等识图问答不在 P0 范围。注意与"课程正文文本化"是两件事——文本化是离线批量，不需要运行时识图
services/code_ingest_service.pyFDE 课程代码包入库能力，无对应场景
auth_service 的角色体系登录体系不搬：需对接官网 /login，而非自建用户名密码
frontend/（Vue + Element Plus）官网是 Vue 3 + Ant Design Vue，组件库不同；只借鉴交互模式与接口契约

核心动作：未命中时发生了什么

POST /ask  { question, course_id, channel }
   │
   ├─ 已登录？ ── 是 → 沿用 FDE 逻辑（空间来自 space_members）
   │            └ 否 → 签发匿名 id，空间写死为 courses   ← P0 改造点
   │
   ├─ 检索 → 过阈值 → 调模型作答 → 返回 sources（模型无法篡改来源）
   │
   └─ 未命中 → 转人工三级路由
                1. course_id 精确匹配 topic_owners
                2. 问题关键词匹配课程别名
                3. 兜底码（未配置则 configured=false，绝不编造）
                → 落一条线索（tickets 表）
                → 返回 owner.contact（售前企微活码）+ 未命中文案
这一步的意义

官网现状是：用户要先点「咨询」→ 弹二维码 → 扫码 → 跳出官网 → 加好友 → 等人工，共五步，且覆盖不到自然流量与非工作时段。
P0 把这条路径改成：Agent 先答，答不上来才扫码——把"扫码"从第一步变成最后一步。

自检脚本：验证复用结论是否站得住

scripts/smoke_kernel.py 覆盖八组断言，且不需要数据库、模型或 API Key——因为它验证的是"内核剥离业务后是否完好"，而不是业务本身：

检查组断言要点
内核模块可导入含 embed / rerank 的重依赖延迟导入是否成立（决定能否在无 torch 环境下复用）
P0 配置课程空间、网关地址、游客 Cookie、转人工开关、门控阈值
分块器课程详情页长文能否直接吃进去、是否超长、内容是否丢失
词法切分jieba 缺失时应降级而非报错
RRF 融合去重是否正确、双通道命中者是否排第一、是否保留 dense 分
空间过滤空空间与非法 top_k 必须直接返回空，不做全库检索
游客与转人工游客空间写死；数据库不可用时转人工必须降级而非抛异常
数据模型线索字段就位、工单约束已放宽、映射表字段齐全

执行方式：python scripts/smoke_kernel.py。

实测结果：40 项断言，0 失败

在只安装轻量依赖（不含 torch / sentence-transformers）的隔离环境中执行，全部通过。这直接证实了三件事：

  • 内核模块确实可以在无模型环境下被导入与测试，重依赖延迟导入的设计成立；
  • 分块器可直接吃下课程详情页的长文本（实测 1350 字切为 2 块，最大 781 字，无内容丢失）；
  • RRF 融合、空间过滤、游客态、转人工降级、线索字段全部按预期工作。

九、风险与降级设计

风险影响已内置的降级
转人工解析失败 把"知识库没答上来"升级成"整个服务挂了"——最严重的一类体验事故 解析异常被捕获并降级为"未配置"，不向外抛错；自检脚本专门断言此路径
课程未文本化 问答全量未命中，P0 失去验证意义 优先文本化 4 个必需板块；未完成前不建议上线
售前企微能力边界未确认 影响 contact 的形态（活码链接 / 静态二维码）与自动归因能否成立 映射表只存"一串联系方式"，不预设渠道能力；能力确认后换数据即可，不改结构
映射表只支持单个负责人 同一课程无法按人分流 P0 不做分流；需要时加子表，属已知结构限制
多副本部署时限流失效 限流与指标为进程内实现 P0 单副本运行即可；多副本需引入共享计数（沿用 FDE 的上线差距结论）
