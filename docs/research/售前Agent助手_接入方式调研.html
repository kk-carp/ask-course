售前 Agent 助手 · 市面接入方式调研

目的 用行业实证校验官网接入方案，找出更优路径与遗漏项 方法 厂商官方接入文档 + CSP 专题 + 官网响应头实测 日期 2026-09-16 配套文档 售前Agent助手_需求分析报告（3.3 接入方式）

本次调研覆盖 9 类接入形态、13 个代表性产品，并实测了天树探界官网的部署与响应头现状。三条核心结论：

一、行业默认做法就是"一行 script + Shadow DOM"，我们的首选方案得到验证
国际（Intercom / Chatbase / Chat.co / Agentkit / Clanker）与国内（美洽 / 七鱼 / Dify / FastGPT）产品的首选接入方式高度一致：往页面底部注入一段异步脚本，脚本把组件挂载到 document.body 的 Shadow DOM 里。我们此前定的 P1「部署层脚本注入」不是权宜之计，而是行业标准做法。
二、真正的分水岭不是技术，是"谁能改这一行代码"——因此行业另有一条无代码通道
对无法直接改代码的团队（营销团队、外包维护、有变更管控的组织），行业的标准答案是标签管理器（GTM）自定义 HTML 标签：可版本化、可灰度、可回滚，且不碰官网代码。我们原方案缺这一条。实测官网当前未部署任何标签管理器，因此该路径暂不可用，但值得列为备选。
三、实测：官网为 Nginx 部署、响应头未包含 CSP——"注入会被 CSP 拦截"这一顾虑当前不成立
实测 www.arborseek.com 首页响应头：Server: nginx、Access-Control-Allow-Origin: *，未见 Content-Security-Policy，也未见 X-Frame-Options；页面仅挂一个主 JS 产物与百度统计，无 GTM / dataLayer。含义有两面：当前注入不会被浏览器拦截、iframe 方案也不受 frame 限制；但站点日后一旦启用 CSP，接入会被整体拦截，故仍需向官网确认"是否有启用计划"。

二、六条行业共性约定 可直接照搬的工程惯例

1 · 脚本放 body 末尾、异步加载、重界面按需加载

七鱼文档明确要求代码"添加位置必须在 body 内，若放置在 header 中将无效"；Chat.co 建议加 defer；Agentkit 的做法是"首屏只加载一个很小的脚本，完整对话界面在用户点击气泡时才加载"——把对页面性能的影响压到最低。这对官网这类以内容展示为主的站点很重要。

2 · 用 Shadow DOM 做样式隔离 直接对应本项目的样式冲突风险

Clanker 官方文档原话："脚本把 widget 挂载到附加在 document.body 上的 Shadow DOM 中，因此站点的 CSS 无法破坏 widget，widget 的样式也不会泄漏到页面。"

官网是 Vue 3 + Ant Design Vue，组件库带有大量全局样式与 z-index 层级。Shadow DOM 是行业用来避免这类冲突的标准手段，应写入技术方案，而不是等联调时再补。

3 · 匿名优先，登录后升级 与本项目主战场完全吻合

Intercom 官方文档："你可以为未登录的匿名访客安装 Messenger，只需从设置对象中省略用户信息——会话通过浏览器 cookie 保存。"登录后再调用 boot 并带上 user_id / email 完成身份升级。

这是一个重要的定位确认：在行业实践里，"未登录访客"是正常的一等状态，不是需要特殊处理的异常分支。我们的 Agent 主战场正是未登录游客，因此应当照此设计——匿名可完整使用问答与推荐，直到转人工或下单才引导登录。这与 R9 登录态保持并不冲突，而是它的前半段。

4 · 身份凭签名校验，密钥绝不进前端

Intercom 的做法是服务端用密钥签发 JWT（HS256，载荷含 user_id，建议短过期），前端通过 intercom_user_jwt 传给组件；官方明确"密钥永远不应出现在前端代码中"，且未启用签名保护时只开放最近 14 天会话作为兜底。含义：Agent 若要把官网登录态转成自己的会话身份，应由服务端签发短期凭据，前端只做透传，而不是把官网 token 直接交给第三方组件。

5 · 登出与切换账号必须显式清理

Intercom 文档警告：会话 cookie 默认存活 7 天；在共用设备上，"下一个使用者可以看到上一位登录用户的会话历史"，因此登出时必须调用 shutdown() 结束会话并清除 cookie。

这条直接对应本项目的合规风险（R19 要留存会话内容做归因）。既然行业对同类问题给出的解法是"登出即清 + 明确告知"，我们的会话留存口径也应包含这条，否则在共享设备场景下会把 A 的咨询内容展示给 B。

6 · SPA 必须专门适配，且路由监听不能绑死 重要警示

Intercom 文档："如果 URL 变化但没有整页刷新，Messenger 不会自动把 URL 变化发送给 Intercom"，需主动调用 update；且 update 调用被限制为每用户每页面最多 20 次，超出即被限流，配额每 30 分钟重置。

我们此前判断"SPA 路由可监听 history 变化，埋点可自闭环"——方向没错，但行业实践给出了两个具体警告：一是不会自动同步，必须显式处理；二是频繁上报会被限流。因此我们的埋点应以 Agent 自身的交互事件为主体，把路由变化作为上下文补充而非主键，并对上报做节流合并。

三、CSP：行业公认的头号接入障碍 也是唯一可能整体推翻方案的变量

一个客观信号：Intercom、Tidio、Velaro、Alive5 等厂商都专门维护了"CSP 配置"帮助文档，说明这是第三方组件接入时最普遍的摩擦点。三个容易被低估的细节：

要点行业事实对本项目的含义
需要放行的是一组指令 不只是 script-src，还包括 connect-src（含 wss:// WebSocket）、frame-src、img-src、font-src。Tidio 的配置指南指出 WebSocket 地址最常被漏掉。 与官网谈 CSP 时不要只说"加一个白名单"，要提供完整指令清单，否则会反复返工。
strict-dynamic 会忽略域名白名单 Intercom 案例研究：存在 nonce + 'strict-dynamic' 时，支持该特性的现代浏览器会忽略 script-src 里的域名白名单——这是规范行为而非缺陷。 如果官网采用 nonce 方案，我们的域名白名单可能形同虚设，需按"由 nonce 脚本动态注入"的路径设计。
跨文档上下文的 nonce 信任不可靠 Velaro 文档：组件分两阶段加载（shim 脚本 → 沙箱 iframe），由于 iframe 是独立文档上下文，nonce 的信任传播不能跨浏览器可靠生效，因此必须在 script-src 中显式列出域名。 若采用 iframe 降级方案，CSP 沟通的成本反而更高——这削弱了 iframe 作为"更省事"选项的假设。
实测现状与沟通口径的调整
实测官网首页响应头未见 Content-Security-Policy，因此当前不存在拦截问题。但"当前没有"不等于"以后没有"——一旦官网出于安全合规启用严格 CSP，注入会被整体拦截。

据此，《官网技术负责人_确认问题清单》的 B3 项已改为确认"未来"而非"现状"："站点后续是否有启用 CSP 的计划？若启用，能否为本项目预留 script-src / connect-src（含 wss:// 流式通道）/ frame-src 白名单？"同时 B3 由阻塞项降为高优先级（阻塞项收敛为 B2 部署层注入权限、B5 迭代优先级、B9 企业微信能力边界三项），并在会前材料清单中注明"现状已由我方实测，无需对方再查"。

四、安全侧：第三方脚本的行业防护基线 此前方案未覆盖，但安全评审必定会问

行业对第三方脚本的风险描述是一致的：外部脚本以你站点的 origin 全权限运行——可读 Cookie、读表单内容、改写 DOM。历史上 Polyfill.io、Magecart 等供应链事件都属此类。因此官网技术团队在评审时提出质疑是合理的，我们应主动准备答案而非被动应答。

行业手段做法我们可以给出的承诺
SRI 子资源完整性给脚本加 integrity（SHA-384）+ crossorigin="anonymous"，浏览器校验字节不一致即拒绝执行。要求版本化 URL，禁用 latest.js。加载器脚本固定版本、可提供哈希供官网校验。
加载器与内容分离Clanker 的做法值得借鉴：加载器脚本只有 5 个固定配置项，其余配置在运行时从后端拉取，因此脚本本身可长期不变。这是解决 SRI 与"远程可更新"矛盾的关键设计——加载器冻结（可加 SRI），业务内容走自有 API。
CSP 与 SRI 配合CSP 管"只信任这些域名"，SRI 管"只信任这个确切文件"。OWASP 有专门条目。可主动提供 CSP 白名单清单，降低对方评审成本。
版本与回滚脚本 URL 带版本号；注入支持远程开关，出问题即时停用。写入 R26：注入必须可摘除、可版本切换。

五、承接侧：企微「联系我」的接入事实 决定 R19 自动归因能否成立

售前承接渠道已升级企业微信。就"线索归因"这一条，企微官方开发者社区与接口文档给出的约束比预期更严：

能力事实结论
渠道区分 「联系我」可配置 state 参数（≤30 字符）用于区分渠道；客户添加时会触发"添加企业客户事件"，回调中返回该 state。 R19 自动归因技术上成立
配置前提 只有通过 API 创建的「联系我」二维码才能配置 state；在管理后台创建的，API 侧读取不到。 前提条件必须改用 API 创建活码
数据统计 企微后台不直接提供某个活码的客户总数与流失数；官方建议"收到删除事件后自行保存本地统计"。 需自建统计
数据完整性风险 开发者社区明确指出：若企业成员被移出可见范围，服务商可能收不到添加或删除事件，自建统计会遗漏。 归因数据需标注"可能存在遗漏"，不能作为唯一凭证
对本项目的直接含义
R19「线索来源自动归因」能不能落地，取决于三件事同时成立：① 售前活码改为通过 API 创建并配置 state；② 开通并订阅客户联系事件；③ 自建一份归因统计（含事件漏收的容错处理）。三者缺一，都需回退到"Agent 侧弱归因 + 售前人工回填"的降级方案。这使 B9 的确认清单更具体：不只是问"是否启用活码"，而是问"活码是否由 API 创建、能否配置 state、能否订阅添加/删除客户事件"。

六、与既有接入路径的对照 哪些得到验证，哪些需要补

既有路径行业对应结论
P0 独立部署先行无直接对应（行业假设一定有前台流量）行业没有这种做法，但对"先服务内部、先验证质量、不等授权"的目标是完全合理的取舍，且业界常见于自建系统的内部试点期。保持不变。
P1 部署层脚本注入全部主流厂商的默认/推荐方式验证通过，仍是首选。补充两点行业惯例：Shadow DOM 隔离、重界面按需加载。
P2 单点组件替换NPM / 框架 SDK 组件集成保持。官网为 Vue 3，若日后拿到源码，可直接走组件集成。
P3 完整前端集成API + 自建前端保持为目标态。
新增 · 标签管理器通道GTM 自定义 HTML 标签（行业对"无代码权限团队"的标准答案）建议补入方案作为备选。优势：不碰官网代码、自带灰度与回滚、可由业务侧自助维护。实测官网当前未部署任何标签管理器，需官网先接入才能走这条路——可作为与官网技术谈判时的替代方案提出。

七、落地检查清单 可直接作为技术方案与安全评审的自检项

  1. 挂载：脚本注入部署层（</body> 前），全站生效；组件挂载进 Shadow DOM，与 Ant Design Vue 样式完全隔离。
  2. 性能：加载器异步且轻量；完整对话界面在用户首次点击时加载；验证首屏指标无劣化。
  3. 身份：匿名访客可完整使用问答与推荐；登录后由服务端签发短期凭据完成身份升级；官网 token 不直接进入第三方组件。
  4. 会话：登出或切换账号时显式清空本地会话与标识；共享设备不泄露上一位用户的咨询内容。
  5. SPA：路由变化显式捕获并节流合并，不作主键；埋点以上报节流为前提，避免高频上报被限流。
  6. CSP：向官网提供完整白名单清单（script-src / connect-src 含 wss / frame-src / img-src）；确认官网是否有启用 CSP 的计划。
  7. 安全：加载器脚本版本固定、可提供哈希；业务内容全部走自有 API 拉取；注入支持远程开关与快速摘除。
  8. 归因：售前活码确认由 API 创建并配置 state；订阅添加/删除客户事件；自建统计并对漏收做容错，标注数据完整性限制。
  9. 降级：明确 P1 → iframe → 独立页三种形态的切换条件，以及转人工链路的兜底码。
