文档说明
本细则把 PRD 中「怎么问、推什么、为什么推、什么时候转人工」四件事写到可直接开发与验收的粒度，对应功能模块 M2 对话与问诊、M3 推荐引擎、M6 转人工与线索。
编号体系与 PRD 完全一致：R 沿用需求池，M 为模块，EARS 为需求条目，PL-01–PL-12 为 PRD 待补占位项。本细则新增的、PRD 尚未收录的缺口以 G-01–G-03 标记（见第 15 章），建议下次修订时合并进 PRD 的 PL 列表。
凡标注「待补」处，均为受 PL 或 G 项阻塞、当前不可定稿的内容；未标注部分为已确定规则，可直接进入评审与开发。

1. 设计原则

  1. 少问、快答。问诊是采集"最小充分信息"，不是填表。必答字段控制在 4 项，全程不超过 5 轮；其余画像在对话中自然获取，不额外增加轮次。
  2. 先承接，不设门槛。全程不需要登录、不需要加微信。登录只出现在真正要付款的那一刻（对应 U-05 / X-01）。
  3. 推荐必须可解释。每条推荐理由都要落到一个真实字段值上；无依据的推荐等于没有推荐（对应 U-01）。
  4. 转人工的标准是"人工答得更好"，不是"机器答不出来"。敏感意图是主动转，不是兜底转（对应 U-04）。
  5. 宁可少推，不可乱推。硬匹配只排除"明显学不了"的课程；不确定时降权与提示，而不是直接排除。
  6. 一切口径以接口为准。价格、难度、时长、证书、优惠均取自课程接口或知识库；接口没有的，说不确定并转人工。

2.2 字段状态与「未知」处理

每个字段都有三种状态：已采集 / 未知 / 明确不适用。三者在排序中的处理不同，必须区分：

状态判定排序处理
已采集用户点选或明确表述该因子正常计分
未知用户未提及、回避、或问诊轮次已用尽该因子不计入，其权重按比例分摊给其余因子——不得按"不匹配"计零分
明确不适用用户明确表示"不在意"该因子不计入，也不分摊（视为无约束）
为什么必须区分"未知"与"不匹配"
把"没问到"当成"不匹配"，会让信息量少的用户拿到更差的推荐，且推荐结果会集中到卖点最全的课程上。未知只能导致"该维度不参与比较"，不能导致"扣分"。

3. 问诊脚本

3.1 开场（不计入轮次，按上下文分四种）

A · 从课程详情页进入（能解析到课程）你在看《{课程名}》。想确认它适不适合你，还是想让我帮你比较几门？
B · 从首页或课程列表进入帮你选课 —— 先了解你的情况，大概 4 个问题，1 分钟出结果。不需要登录，也不用加微信。
C · 带售前引流来源参数，或对话中已指明课程（不走问诊）你要的是《{课程名}》，直接给你入口和关键信息。
D · 存在未完成的购买意图你上次看过《{课程名}》还没下单，要接着看吗？

3.2 逐轮脚本

轮次问题（Agent 说法）选项分支与规则
1 先确认一下你现在的身份？
P1		 在校学生 / 在职工程师 / 高校教师 / 企业或团队 / 其他 企业或团队 → 不走课程推荐，收集单位、人数、用途后转 B2B 通道；
高校教师 → 继续问诊，课程范围含教师培训与赛事类；
其他 → 走语义归一（3.4）
2 你目前的技术基础大概在什么程度？
P2		 零基础，没写过代码 / 会一点编程 / 有机器人或 AI 基础 / 做过实际项目 映射难度上限：零基础 → 难度 ≤1；会一点 → ≤2；有基础 → 2–3；有项目 → 2–3 并提高 F2 得分
3 你更想达成什么？最多选 2 项
P3		 先入门看看 / 系统学一套 / 做个能跑起来的项目 / 竞赛或考证 / 找工作 / 教学备课 竞赛或考证 → 追问一次具体赛事（关联课程标签），只追问一次；
找工作 → 标记"就业导向"，项目实战线提权；
多选超 2 项 → 取排序前 2
4 你手边有哪些设备？这决定哪些课你能直接动手做
P4		 只有电脑 / 有开发板（树莓派、ESP32 等） / 有机械臂或机器人本体 / 不确定，得看课程要求 本轮的答案直接决定硬件硬匹配（H1）；即使 P2 为零基础也必问——实机类课程的门槛与基础无关

第 4 轮结束后即输出推荐（EARS S-01）。轮次上限为 5 轮：若第 5 轮结束仍有字段缺失，直接出推荐，缺失字段按「未知」处理。

3.3 跳过、提前结束与退出规则

触发情形系统行为依据
用户在任何一轮指明具体课程名称立即终止问诊，进入短路径（第 4 章）EARS S-02 / E-03
命中敏感意图或效果承诺类提问立即终止问诊，进入转人工（第 10 章 T1）EARS X-02
用户说"你直接推荐""别问了"用已采集字段直接出结果，并说明"按你目前说的来推"本细则
同一问题被连续回避 2 次该字段标记「未知」，不再追问本细则
学员已是已购状态（is_enrolled）停止问诊与推荐，转售后引导EARS S-04
身份为企业或团队停止课程问诊，转 B2B 通道PRD 4.5
用户中途离开保留已采集画像；再次打开时询问是否继续上次的选课EARS U-05

3.4 追问与语义归一

  • 一次只问一个问题，不并列多问，避免表单感。
  • 用户自由输入时，先归一到最接近的枚举值，再用一句话复述确认："我理解你是{枚举}，对吧？"——只确认一次，用户不认可则直接采用其原话并按未知处理相关因子。
  • 用户前后信息矛盾时，以最新表述为准并静默覆盖，不反复澄清；若该信息直接影响推荐结论，用一句话说明："按你最新说的{结论}来推。"
  • 用户输入与选课无关、或语气不友好时，不纠缠、不教育，回到上一个未完成的问题。

4. 短路径与已决策判定

短路径的目标是：对已经想清楚的人，不要重问一遍（US-04）。判定条件满足任一即进入：

触发条件判定方式动作
链接带售前引流来源参数解析 URL 参数，标记 S1 = 售前引流问诊轮次 = 0；同时降低主动唤起频次（E-01）
对话中指明课程名称与课程库 title / subtitle 做模糊匹配加载该课程上下文，跳过问诊
从详情页进入且刚点击过购买捕获点击行为直接给购买入口与条款确认
存在未完成购买意图本地留存 last_purchase_intent开场提示继续，不重新问诊

短路径下的输出内容（不展示推荐卡片，除非用户主动要求）：

  1. 课程名称、价格（含阶梯价）、有效期、难度、适用人群；
  2. 购买入口按钮，以及"未登录也能先问"的说明；
  3. 一句兜底："还有想确认的可以直接问我，价格和退费类问题我会转人工。"

5. 课程属性字典与内容文本化的最小范围

推荐规则要用的课程属性，按来源分为三类。这个分类直接决定了"哪些内容必须先文本化"（对应 R28 / PL-11）：

编号课程属性来源可靠性用途
C1课程线 / 分类列表与推荐接口 category详情接口未含分类呈现、课程线限流
C2难度接口 difficulty_level（1–3）结构化可靠硬匹配 H2、基础适配度 F2
C3价格（含阶梯价、原价）接口 price / original_price / price_tiers类型待统一（PL-03）价格带契合 F4、话术
C4授课形式与学习模式接口 course_type / learning_mode / unlock_mode结构化可靠期望管理、F5
C5有效期接口 validity结构化可靠条款确认
C6标签与卖点接口 tags[] / course_features[] / subtitle结构化可靠卡片渲染、理由素材 F1
C7师资接口 teachers[] / tutor样本为空师资类答疑
C8适用人群详情页第 7 板块（正文为图片）需文本化硬匹配 H1 / H3 的核心依据
C9课程目录 / 大纲详情页第 5 板块（图片，疑需独立接口）需文本化判内容范围与硬件需求、理由素材
C10学习安排 / 时长详情页第 2 板块（图片）需文本化时间投入匹配 F5
C11结业证书详情页第 6 板块（图片）需文本化证书诉求匹配 F6
C12售前二维码接口 pre_sale_service_qrcode结构化可靠转人工路由
C13体验课与正价课配对由同名 / 近名产品推断（如四足机器人巡检 ¥5.9 / ¥599）推断阶梯呈现（第 8 章）
结论：文本化只需先覆盖 4 个板块，不必全量
C8 适用人群 · C9 课程目录 · C10 学习安排 · C11 结业证书——这四项是推荐规则唯一依赖文本的部分，也是目前图片化最严重的部分。其余板块中，讲师团队（C7 已有接口字段，样本为空）与授课形式（C4 已有接口）可后置；往期回顾信息密度最低、图片最多，优先级最低。
这条结论可直接用于给课程运营排 OCR 与补录的先后顺序：先补 Top 20 课程的这 4 个板块，其余课程按同样顺序批量转文本。

另需注意 EARS E-04 的约束：未完成文本化的课程，不得凭标题推测内容——其推荐理由只能使用 C2 / C3 / C5 / C6 这类结构化字段，并在回答内容类问题时明确引导查看页面。

6. 硬匹配规则

硬匹配的唯一目标是排除"明显学不了"的课程，不做精细筛选。宁可少排除，也不要误杀。

编号规则判定动作
H1 硬件门槛 课程属实机实训类（依据 C8 / C9 文本），且 P4 = 只有电脑 / 不确定 排除；若该课程文本中明确提供仿真替代方案，则保留但降权，并在理由中说明"可以先用仿真环境"
H2 难度倒挂 C2 = 3 且 P2 = 零基础 排除
H3 身份错配 课程仅面向教师或企业（依据 C8 文本），且 P1 = 在校学生 排除
H4 推荐范围 非天树探界自有课程 排除（EARS U-03）
H5 不可报名 can_join = false，或课程已下架 排除
H6 已购去重 is_enrolled = true，或已购章节覆盖该课程主体 停止推荐，转售后引导（EARS S-04）
H7 内容不可判定 P3 含"项目"或"竞赛"，需依据课程内容判断，但该课程尚未文本化 保留 + 降权 + 提示（不排除）——"这门课的具体内容建议看页面说明"（EARS E-04）
H1 是唯一可能"误杀"的规则，需特别处理
硬件门槛判错会直接丢掉一个真实的意向线索。因此 H1 的判定只有在 C8 / C9 文本化完成后才可启用；文本化之前，实机类课程一律走降权 + 提问确认，不直接排除。这是文本化工作必须先于推荐规则上线的原因。

7. 软排序规则

硬匹配后的候选课程按下列因子加权排序，取 Top 3（与 EARS S-01 的 2–3 门约束一致）。

编号因子计算依据初始权重
F1目标契合度P3 学习目标 ↔ 课程目标能力（C6 卖点 / tags / C8 适用人群）35%
F2基础适配度P2 技术基础 ↔ C2 难度（同档满分，每跨一档递减）20%
F3硬件可满足度P4 硬件条件 ↔ C8 / C9 的硬件要求15%
F4价格带契合P7 预算 ↔ C3 价格10%
F5时间投入匹配P6 每周可投入 ↔ C10 学习安排时长10%
F6证书诉求匹配P8 证书诉求 ↔ C11 结业证书5%
F7运营因子课程线线索承载饱和度（S-06）· 内容文本化完整度 · 是否存在体验课升单路径5%

7.1 排序规则要点

  • 未知字段不计入，其权重按比例分摊给其余因子（见 2.2）。
  • 同分时的优先级顺序：① 有体验课可先试 ② 内容已完成文本化 ③ 价格更低 ④ 课程线上线时间更近。
  • 权重为初始值，属可配置项，由产品侧按上线后的实际表现调整，不需发版、不需评审。调整推荐权重不影响业绩归属——归属规则独立于推荐结果（对应 R25 的定位）。
  • 推荐结果的课程线分布需可持续出数，供销售侧核对是否存在系统性偏向（对应 R7 的透明度措施）。

8. 阶梯呈现规则

"先低价试 → 再升单"是本项目的核心转化路径，必须在推荐结果里被显式表达，而不是靠用户自己发现。

编号情形呈现方式
L1结果中存在体验课—正价课配对（C13）同屏呈现，体验课在前，并标注关系："¥5.9 体验课 → ¥599 正价课，前者是后者的第一模块"
L2用户明确"想系统学一套"，且 P7 预算覆盖正价课正价课排前，体验课作为次要选项（"也可以先花几块钱试一节"）
L3结果数量最多 3 门；同一课程线不超过 2 门，避免选择过载
L4课程明显低于用户基础降级或剔除——给已做过项目的人推零基础入门课，等于告诉他"你没被听懂"
L5体验课 CTA 的突出展示条件仅在三种情形下突出：① 用户表达价格顾虑 ② P7 预算低于正价课价格 ③ 首次到访且目标为"先入门"

9. 推荐理由生成规则

9.1 四条硬规则

  1. 每条理由至少引用一个真实字段值——课程字段（C2–C11）或用户自己说的画像（P1–P8）。
  2. 禁止推测课程内容。内容未文本化时，理由只能来自难度、价格、时长、形式、标签等结构化字段。
  3. 长度不超过 2 句，先给结论再给依据，不写形容词堆砌。
  4. 不得出现承诺（折扣、退费、包就业、证书效力、收益预期）。

9.2 模板

模板 A · 画像驱动你说{用户原话摘要}，这门课的{板块或字段名}写的是{字段值}，属于{结论}。
模板 B · 对比驱动和{另一门课}比，这门{字段}是{值}，更适合你现在的情况。
模板 C · 阶梯驱动这门{体验课}先花{价格}试{内容范围}，觉得合适再上{正价课}。

13.2 上报节流规则

  • 路由变化不新增事件，只更新公共属性（page_type / course_id）。行业同类组件的做法是把 URL 变化当作属性更新而非独立事件；单页应用里高频的显式上报请求还会被限流，节流合并是必需的，不是优化项。
  • 同一事件在 1 秒内多次触发时合并为一次，并记录触发次数。
  • 会话级事件（session_start / session_end）按会话去重，不重复上报。
  • 批量上报，避免逐条请求。
待补 · PL-07 支付完成事件 "是否完成支付"无法由 Agent 侧自闭环，需官网或后台提供支付结果回传。责任方：官网技术。该事件未落定前，北极星指标只能统计到"转人工 + 线索落库"为止。
