综合判断如下十点：

  1. 官网不是售前主战场，微信才是。当前真实的成交路径是「售前人员在微信上与学员一对一沟通 → 引导学员到官网完成支付」。官网在整个链路中承担的是收银台角色，而不是咨询与决策场所。这决定了本方案的首要命题不是"填补官网空白"，而是"与人工售前如何分工"。
  2. 班主任企业微信是售后入口，不是售前入口。经确认，班主任企微在学员付费之后才可见，属于班级服务与学习管理通道。
  3. 官网并非没有承接点，而是承接点"太重"。官网上设有咨询按钮，点击后弹出售前人员微信二维码，且不同课程弹出的是不同售前人员的微信。承接是存在的，但完整动作是"主动点击 → 扫码 → 跳出官网 → 加好友 → 等人工回复"，共五个环节。它能否生效，取决于用户愿不愿意扫以及售前在不在线。该二维码已升级为企业微信——通道具备可统计、可编程（活码与开放接口）的能力基础，线索归因与上下文传递因此可实现（见第 1 节、3.1 与第 12 节）。
  4. "按课程路由到售前"这件事，官网已经在做了。既然不同课程对应不同售前微信，说明课程—售前映射关系已经存在，售前团队本身也是按课程线分工的。这对方案是重大利好：R6（按意向课程转人工）从"需要新建分配机制"降级为"读取并复用现有映射"。但它也意味着 Agent 推荐哪门课、线索就流向哪位售前，推荐逻辑在客观上具有分配作用。归属规则确认为"归属最近一次人工接触的售前"，带来一个关键效果：已被售前接触过的学员，其业绩不因 Agent 介入而转移——售前的存量利益被保护，内部抵触动机因此显著下降；剩余关注点收敛为"增量自然流量线索的分配"与"各课程线承接能力"（见 2.5）。
  5. 因此 Agent 的位置很清楚：把"扫码"从第一步变成最后一步。先在官网内部用 Agent 完成常规答疑与选课推荐，只把价格让利、B2B 采购、复杂个案交给扫码转人工。不是替代人工，而是把人工的产能留给最值得人工介入的对话。
  6. 售前人员的微信对话记录是知识库的最佳素材。学员在微信里问过什么、卡在哪一步、什么话术能促成转化——这些真实语料比从零设计问诊脚本准确得多。这是本期成本最低、收益最高的准备动作，建议列为 MVP 前置任务。
  7. 六项正面发现降低了实现成本：课程详情页已有 9 个标准板块可直接作为推荐匹配字段（见 1.1）；官网已有的二维码弹窗本身就是现成的转人工出口，Agent 可直接复用（见 3.1）；课程—售前映射关系已经存在，按课程路由不需要重新设计分配机制（见 3.1）；售前承接渠道已升级为企业微信，为线索归因与上下文传递补上了可编程基础；公司另有一套已落地的同类系统（FDE「统一知识助手」），其 RAG 内核、「未命中 → 转人工」链路、负责人映射表、旁路推荐 Agent 编排与评测闭环均可直接复用（见 3.2）；课程详情接口经实测返回完整结构化字段，且售前二维码即为现成的接口字段（见 3.4）。
  8. 接入官网不依赖前端源码，需要的是"三处授权"。即使目前没有官网代码，Agent 也可以通过在部署层注入脚本的方式挂载上线——这正是第三方客服系统的标准做法，它对官网的要求只是"在 HTML 中多一行 script"。真正需要拿到的不是整套源码，而是：部署层的一处注入权限、现有"咨询"弹窗的组件位置、以及课程—售前映射的读取方式。更重要的是，在这些授权到位之前，Agent 完全可以先独立部署、先服务售前内部，不受任何阻塞（见 3.3）。现官网维护方已确认为内部技术团队：三处授权可直接与内部团队沟通、不跨组织；且内部团队具备改源码能力，P2（单点组件替换）与 P3（完整集成）也更具可行性，入口归一（R22）可借源码改造更干净地实现。
  9. 三项组织规则已落地，这是立项阶段最重要的进展。① 人机分工确定为协同（C）+ 增强（B）——官网侧 Agent 承接初步问诊并把高意向线索按课程交付给对应售前，内部侧为售前提供推荐与话术辅助；② 业绩归属确定为归属最近一次人工接触的售前，售前存量利益受保护；③ 推荐权重暂不设评审机制。三条落地后，方案最大的不确定性由"组织能否接受"转为"能否按期实现"，项目可以从需求分析进入 PRD 撰写（见 2.5）。
  10. 课程详情接口已实测，两项关键未知同时关闭，但暴露出一项内容风险。接口返回结构化的课程 JSON，且直接携带 pre_sale_service_qrcode（售前服务二维码）字段——"课程 → 售前"的映射无需另寻数据源，按课程 ID 调用详情接口即可取得，R24 的实现方式确定为字段直读。推荐所需的字段（价格、原价、标签、分类、难度分级 difficulty_level、卖点、报名状态）也比预期更完整。但需正视一项新风险：课程正文 full_description / h5_description 全部由图片构成，接口层没有可检索文本——而"这门课讲什么"正是学员最高频的提问，知识库必须另行文本化（见 3.4）。

修订后的判断分三层：

  1. 对"被售前带过来的学员"，链路是通的——决策已在微信完成，官网只需完成登录与支付，Agent 在此处的价值是降低临门一脚的摩擦。
  2. 对"自己找到官网的学员"，链路不是断的，但很窄。要走到人工面前，必须先主动点击"咨询"、愿意扫码、愿意离开官网到微信里再聊、还要碰上售前在线。每一个环节都是一次筛选，绝大多数自然流量走不完这四步。
  3. Agent 的介入位置因此非常明确：把"扫码"从第一步变成最后一步。先由 Agent 在官网内部承接常规问题（课程内容、难度、基础要求、证书、价格区间、如何选），只有在用户明确要求找人或遇到敏感问题时，才弹出二维码。由于现有弹窗已按课程区分售前，"弹对了码"本身就是一次有效的线索分流——Agent 只需按推荐结果取对应售前即可。这既不削弱人工，反而提高了交给人工的对话质量，也让线索落到了对的人手上。

2.5 关键定位决策：Agent 与人工售前的三种分工关系

这是本方案最需要优先拍板的问题，它决定产品形态、工作量与内部推广阻力，优先级高于任何功能清单。

路线形态优势风险建议
A. 替代 官网自助售前机器人，直接面向学员 覆盖自然流量与非工作时段；边际成本低 易被售前团队视为"抢单"；缺少人际信任，高客单课程说服力弱 部分采纳
B. 增强 售前人员内部助手：在微信对话过程中实时给出推荐结果与标准话术 不触碰业绩归属；直接提升售前效率；可沉淀真实对话数据用于迭代 需另做内部端；使用意愿依赖运营推动与考核配套 已确认 · 与 C 并行
C. 协同 官网 Agent 承接初步问诊，识别高意向后按课程交付给对应售前人员 同时覆盖自然流量与售前引流；形成"机器初筛 + 人工成交"的分工；复用现有二维码弹窗与课程—售前映射即可落地 需与售前约定响应时效与超时兜底；课程路由已存在，但 Agent 的推荐偏向会直接改变售前的线索份额 已确认 · 核心形态
方案 C 的实现成本比预想低，且通道已具备可编程基础
既然官网已有"点击咨询 → 弹出销售微信二维码"的能力，Agent 的转人工动作就不需要新建任何通道——复用同一个弹窗即可。而且由于不同课程对应不同售前微信，"按意向课程路由到对应售前"这一能力也已经天然具备，无需设计分配算法。承接渠道已升级为企业微信，因此"弹之前先把画像与咨询摘要递过去"具备程序化推送的接口基础（前提是企微「联系我」活码与开放接口已启用）。需要新增的收敛为两件事："判断何时弹"的规则，以及与企微接口的对接实现。
线索分配公平性：风险因归属规则与推荐权重口径落地而显著下降
线索按课程分流到不同售前，因此"Agent 推荐了哪门课"在客观上等同于"把线索给了哪位售前"。两项已落地的规则使风险等级整体下调：
① 归属规则为"最近一次人工接触的售前"——售前已接触过的学员，其业绩不会因 Agent 介入而转移，"被抢单"情形被规则排除，抵触动机显著下降；
② 推荐权重无需销售侧评审——不设评审流程与例会机制，落地路径更短。
剩余关切收敛为两点：一是增量自然流量线索在各课程线间的分配（这是归属规则覆盖不到的部分）；二是各课程线承接能力不均——若某课程线承接力不足，Agent 越努力推荐、线索浪费越严重。
应对措施：保留推荐依据轻量留痕（R25），供事后向售前说明"为什么推这门课"；每月向销售侧同步课程线线索分布作为运营透明度措施（非评审）；按课程线设线索量上限，超出后转兜底分配或降级呈现。
已对齐的组织规则：业绩归属以"最近一次人工接触的售前"为准
规则本身：Agent 促成或辅助的订单，归属最近一次人工接触过该学员的售前人员；Agent 不参与业绩分成，仅计入工具效能指标。
这条规则为什么有效：它把"存量学员"的业绩锁定给已接触的售前，Agent 的推荐结果无法改变既有学员的归属。这直接消解了售前最核心的顾虑（怕被机器抢单），也是内部阻力量级下降的根本原因。
技术含义（重要）：规则要能执行，前提是系统能准确回答"该学员最近一次被哪位售前接触过、在什么时间、通过什么渠道"。因此"最近一次人工接触人"的记录是归属规则的必要前提——须由 Agent 侧与售前侧共同补全（R19 / R27）。
仍待补齐的口径：① 时间窗——多久内的接触算"最近"？② 跨渠道——售前在微信接触、学员从其他渠道进入官网，是否同样判定？③ 纯自然流量成交（无任何人工接触记录）归谁——这是规则的空缺处，需销售负责人补口径。口径未定前，R19 / R27 无法写验收标准。

四项必须改造的结构性问题

  1. 身份模型相反——这是最大的结构性不匹配。FDE 的设计前提是"无开放注册、必须登录才能提问"，检索空间由登录角色计算。而本项目的主战场恰恰是未登录游客（自然流量）。需要在其外增加"游客态"：允许空间指向公开课程知识，且匿名会话必须能持续，直到转人工或下单才引导登录。这是动到鉴权边界的事，不是加一个参数。
  2. 缺少"问诊"这一层——这是最大的新增开发量。FDE 是纯被动答疑（问什么答什么）；本项目必须主动采集画像（身份、基础、目标、硬件条件）后再推荐。该模块在 FDE 中完全不存在，需从零开发。
  3. 推荐对象从"资料"变为"商品"，约束变多。需引入价格带、体验课—正价课阶梯、开课时间，以及"不得承诺折扣与退费"的红线。judge_relevance 的判定标准要从"相关性"改为"适配度"。推荐权重无需销售侧评审，故判定标准由产品与技术共同定义即可，但需对判定依据留痕，以便向用户解释推荐理由（R25）。
  4. 部署形态需重新决定。FDE 是独立 FastAPI 单体（BGE-M3 加载在 API 进程内），官网是 Vue SPA + arboradmin.saikr.com 后台。两条路径：一是 Agent 作为独立服务部署、官网前端嵌 UI（快，建议）；二是把内核移植进现有后台（重）。LLM 侧无阻碍——FDE 使用 OpenAI 兼容客户端 + 可配置 CHAT_BASE_URL，可直接指向 openai.arborseek.com。

3.3 接入方式与前置条件：在"没有官网代码"的前提下如何落地

核心判断：这不是技术障碍，而是协作授权问题
"没有官网代码"这句话最容易被误读为"接不上"。但官网现有状态本身就否定了这个结论：站点持续运营、有独立业务后台（arboradmin.saikr.com）、有 LLM 网关（openai.arborseek.com）、后台还有 AI 供应商管理页。这些都说明存在一支能够改动与部署该站的技术力量，只是产品侧尚未接触到。因此更准确的描述是：产品侧没有代码，不等于公司没有代码。

更进一步，Agent 接入官网并不必然需要前端源码。业界第三方客服系统（美洽、网易七鱼、Intercom 等）接入客户官网的标准方式，就是要求对方在页面中增加一行脚本——它对官网的全部要求是"多一行 <script>"，而不需要交出源代码。本方案可以采用同一模式。

四条接入路径（按前置条件由轻到重）

P0 · 独立部署，先行服务售前内部 一台服务器 + 一个（二级）域名 完全不碰官网 无 知识库问答、推荐查询、标准话术、评测闭环；无前台自然流量 立即启动

四个关键技术判断

  1. 挂载方式：脚本直嵌（Shadow DOM 隔离）优先，iframe 作为保守备选。脚本直嵌无跨域问题、样式隔离可控、可读取同域存储，是主流客服的做法；iframe 隔离更彻底、下线更容易，但有跨域通信与移动端高度适配的麻烦。建议前者，后者的优势仅在于"更容易被运维方接受"。
  2. 登录态：脚本注入方式明显优于 iframe。官网登录态通常存放在 localStorage 或 Cookie 中；注入脚本运行在同域下，可直接读取，不需要官网前端配合。若走 iframe 且跨子域，则必须由官网前端通过 postMessage 主动传递，这就重新依赖了源码改造。结论：R9（登录态与会话保持）在脚本注入路径下的实现难度显著更低。
  3. 课程上下文：即使不改源码也能拿到，但方式要降级。拿不到组件级数据时，有两条替代：一是从 window.location.pathname 解析 /course/:courseId（该路由约定已在 2.4 节确认），即可判断用户当前浏览的课程；二是直接读取详情页 DOM 标题与板块锚点。因此 R10（详情页板块深链）与"感知当前课程"在无源码条件下仍可实现，代价是从接口取数降级为路由解析 + DOM 读取，稳定性略低、需随页面改版维护。
  4. 埋点：Agent 侧可完全自闭环，官网原生行为需要小改造。脚本注入本身就能承担全部 Agent 侧埋点（会话触发、问诊完成、推荐曝光与点击、转人工、来源标识）。真正的缺口只在官网原生行为——浏览路径、详情页停留、是否到达支付页。其中路由跳转可通过监听 SPA 的 history 变化获得，不依赖源码；只有"是否完成支付"这一步需要官网或后台配合。

真正需要拿到的不是代码，而是三样东西

  1. 部署层的一处脚本注入权限（Nginx / CDN / 或前端构建流程中的一处）；
  2. 现有"咨询"按钮的实现位置——用于 P2 复用与完成 R22 入口归一；
  3. 课程—售前映射的读取方式——已实测定案为课程详情接口字段直读（见 3.4），本项只需确认该字段的配置与维护方式。

三者均不要求交付整套源码，属于协作授权范畴。这也是本方案在此前提下的落地要点：把"要代码"的诉求，换成"要三处授权"的诉求。现官网维护方已确认为内部技术团队，沟通对象明确、不跨组织，"三处授权"的可达成性进一步提高；同时内部团队具备改源码能力，P2（单点组件替换）与 P3（完整集成）也更具可行性，入口归一（R22）可借源码改造更干净地实现。

分阶段落地路线

  1. 第一步（现在即可启动，不受任何授权阻塞）：独立部署 Agent，先落"知识库问答 + 未命中转人工"，优先服务售前内部（对应 R21）。既验证检索质量与推荐准确性，也积累真实语料与评测基线。
  2. 第二步：取得部署层注入权限后上线前台悬浮球，跑通匿名自然流量，开始采集分层基线（R7）。
  3. 第三步：与现有"咨询"弹窗合并，完成入口归一（R22），实现"先 Agent 后扫码"的标准动作。
  4. 第四步：取得源码后做上下文深度集成（P3），补齐体验最优项。
无源码路径的三项现实阻力（非技术难点）
① 安全与合规审查：向生产站点注入第三方脚本通常需要过安全评审（脚本来源可信、数据留存与出境、CSP 策略）。② CSP 策略（已实测）：对站点发起的真实请求显示，响应头中当前未包含 Content-Security-Policy，注入不会在此环节被拦截，原设想的"策略拦截"并非现实障碍；但若安全侧后续启用严格 CSP 而未放行本项目来源，已上线的悬浮球会被整体拦截，属上线后才暴露的故障。因此本条仍需向官网确认是否有启用计划并预留来源白名单——"完全不需要对方配合"仍不成立，只是配合点从"解除拦截"前移为"预留白名单"，沟通成本显著下降。③ 内部排期与优先级竞争：脚本注入属官网团队本职工作之外的需求，需明确排入其内部迭代计划、确定优先级与排期窗口，避免被主线需求长期挤占。这三点（安全合规、CSP、内部排期）都应在启动前先摸清，避免在开发末期才暴露。

3.4 课程详情接口实测：字段可用性核对

业务方提供了课程详情接口的真实返回样本（课程 id=40「WorkBuddy AI 助手实战课程」）。该样本同时回答了两个此前悬置的问题：课程数据能否程序化获取，"课程 → 售前"的映射在哪里。

关键缺口关闭：售前二维码就是接口字段
返回体中直接存在 pre_sale_service_qrcode 字段。这意味着"课程 → 售前"的映射不需要另外寻找一张配置表——按课程 ID 调用详情接口即可取得该课程的售前二维码地址。R24 的实现方式由此确定为"接口字段直读"，复杂度为低。

5.2 关键使用场景

  1. 选课困惑（最高频）：面对"ROS2""VLA""具身智能""仿真抓取"等术语，学员无法判断自己该从哪门开始。这是最需要 Agent 介入、也最容易见效的场景。
  2. 不愿扫码的自然流量：学员想先了解清楚再决定要不要加微信。现有入口要求他先做出"加陌生人微信"的决定，这一步挡住了大量只是想问问的人。
  3. 非工作时段咨询：学生晚间与周末是咨询高峰，而扫码后仍需等人工回复，两者天然错配。
  4. 临门一脚的摩擦：已被售前预热、目标明确的学员回到官网时，仍需自行完成登录与下单，中途跳出即前功尽弃。
  5. 售前重复劳动：售前在微信中反复回答相同的价格、难度、基础要求类问题，缺少可复用的标准答案与快速推荐工具。

8. EARS 需求描述（关键需求）

Ubiquitous · 普遍约束
系统应始终基于课程商品库与详情页的真实数据生成推荐与课程信息，不得编造课程名称、价格、开课时间、师资、证书效力与优惠内容。
Event-driven · 事件驱动
当访客在课程详情页连续停留超过 30 秒且未点击购买时，系统应主动展示售前助手入口，并以该课程为上下文生成开场白；若该访客带有售前引流来源标记，系统应降低主动唤起频次，避免与售前人员形成重复打扰。
State-driven · 状态驱动（一）
当会话已采集到"学员身份、技术基础、学习目标"三项必要信息时，系统应输出不少于 2 门、不多于 3 门课程的推荐，并附上每门课的适配理由与价格差异说明。
State-driven · 状态驱动（二）
当系统识别到学员已明确指明目标课程，或该学员由售前人员引导进入时，系统应跳过问诊环节，直接提供该课程的购买入口、开课信息与关键条款确认，不得强制其重新完成问诊流程。
State-driven · 状态驱动（三）
当触发转人工时，系统应依据学员的意向课程，从现有课程—售前映射中取出对应售前人员的微信二维码展示；若该课程无对应售前，或所需售前不在服务时段，系统应展示兜底二维码或通用联系方式，不得展示空白弹窗或与课程无关的售前。
Unwanted · 异常处理（一）
如果学员在未登录状态下发起购买或点击下单，则系统应保留当前会话、画像与推荐记录，并在登录完成后自动恢复至原流程，不得要求用户重新发起咨询。
Unwanted · 异常处理（二）
如果学员的提问涉及价格让利、退费承诺、发票开具、B2B 采购合作，或连续 2 轮无法被知识库匹配，则系统应立即停止自动应答，复用官网现有的二维码弹窗展示该课程的售前人员企业微信，并将画像与咨询摘要同步推送至对应售前（企微接口未开放时，退化为在弹窗内展示可复制的摘要）。
Unwanted · 异常处理（三）
如果学员在非售前工作时段发起转人工，则系统应明确告知预计响应时间并保留会话与画像，且应保证线索落库后于下一个工作时段被交付，不得以"已转人工"作为终止状态而不交付。
Optional · 可选能力
在学员主动点击"咨询"或表达"找人工"意图时，系统应先由 Agent 承接一次问询；仅当学员坚持要求人工、或提问命中转人工规则时，才应展示售前人员微信二维码。

9.2 推荐策略

  1. 硬匹配过滤：以详情页"课程目录"与"适用人群"为主要依据做硬性过滤。无设备的学员不推实机实训营，否则必然流失。
  2. 软排序加权：在候选中按目标契合度、价格带契合度、时间投入契合度加权排序，取 Top 3。
  3. 阶梯式呈现：推荐结果必须体现"先低价试 → 再升单"的路径，例如同时给出 ¥5.9 体验课与 ¥599 正价课，并说明二者关系。
  4. 理由必须可解释：每条推荐需明确说明"为什么推荐这门课"，并优先引用适用人群、学习安排等真实课程字段。
  5. 预热感知与短路径：对已由售前引导进入或已明确指定课程的学员，跳过问诊直接给出购买入口与关键条款确认。
  6. 转人工是收敛而非失败：当问题超出知识库范围时，优先弹二维码而非强行作答。判断标准是"人工答得更好"，而不是"机器答不出来"。
  7. 冷启动方案：初期采用"规则匹配 + LLM 生成理由"的混合方式保证输出稳定；知识库内容优先取自详情页 9 板块与售前真实语料；积累会话数据后再引入向量召回提升精度。

11. 风险与合规提示

风险说明应对建议
双入口冲突官网已有"咨询"按钮，若再叠加 Agent 悬浮球，用户会不清楚该点哪个，或误以为功能重复入口归一：合并为一个入口，先由 Agent 承接，必要时再弹二维码（MVP 必做）

12. 剩余待确认问题

以下问题尚待澄清，建议在 PRD 评审前完成。技术侧的未知已大幅收敛：课程详情接口实测确认售前二维码即接口字段（见 3.4），技术可行性已确认；当前主要待办在内容侧——课程正文与 9 板块以图片承载，接口层无可检索文本。三项组织规则（人机分工、业绩归属、推荐权重）已确认，相关规则类问题关闭；待明确项集中在三处口径补齐：企业微信能力边界、归属判定口径、课程接口数据口径。此外部署层权限虽非功能缺口，但决定接入路径能否成立，建议优先澄清；官网维护方为内部技术团队，重点在于内部排期与授权落地。

  1. 详情页内容可读性：课程接口已实测（见 3.4）：结构化字段可读（价格、标签、难度、分类、卖点、报名状态、售前二维码）；但课程正文与 9 板块内容以图片承载，接口层无文本。待明确：① 是否存在章节 / 大纲、讲师详情、常见问题等配套接口？② 9 板块内容是否全部为图片？③ 若需文本化，采取 OCR 批量转换还是运营补录，由谁承担？
  2. 板块内容完整度：是否所有付费课程都已填齐 9 个板块？哪些课程内容为空？
  3. 售前团队规模与分工：售前人员共几位？日均沟通学员量多少？当前最主要的沟通卡点是什么？分工结构可从现有课程—售前映射反推（知道课程覆盖即可推知按课程线的分工），因此本项剩余缺口主要是人数与产能。
  4. 官网技术团队的协作窗口：www.arborseek.com 由内部技术团队负责开发与部署，产品侧当前无源码属"未对接/未授权"而非"公司无源码"。三处授权可直接与该团队沟通、不跨组织，且该团队具备改源码能力，P2/P3 路径更可行。待明确：该团队的联系窗口、迭代排期，以及脚本注入在其内部的优先级。
  5. 部署层权限与安全审查：是否具备在 HTML 响应中注入脚本的权限（Nginx / CDN / 构建流程）？向生产环境注入第三方脚本需经过哪一层安全与合规评审、周期多长？该注入需求在内部技术团队的迭代排期中处于什么优先级？CSP 一项已实测闭环：站点部署方式为 Nginx，响应头中未包含 Content-Security-Policy，也未部署标签管理器，当前注入不会被拦截；剩余问题仅为"后续是否有启用计划、能否预留来源白名单"。
  6. 售前语料可用性：能否提供历史微信沟通记录（脱敏后）作为知识库与问诊脚本的素材？由谁授权与整理？
  7. 售前二维码字段的配置方式：已实测确认售前二维码即课程详情接口的 pre_sale_service_qrcode 字段，无需另找映射数据源。待明确：① 该字段是否按课程独立配置（实测样本与 tutor.qrcode 指向同一图片，疑似复用班主任码）；② 能否在后台维护——课程新增或售前调整时由谁更新；③ 字段为空时前端现有的兜底逻辑是什么；④ 能否换成企业微信「联系我」活码并带来源参数。
  8. 课程接口的数据口径：实测样本中发现三处需对齐：① price_tiers 阶梯价中"31–60 人 ¥89"高于"1–30 人 ¥69"，单价随人数上升，与常规团购口径相反；② price 为数字而 original_price 为字符串（"199.00"），类型不一致；③ student_count 为 0 而 badge 为 hot，报名人数可能未统计或未对外返回。三项均会影响 Agent 的价格话术与推荐排序。
  9. 倒计时优惠的实际规则：接口返回 countdown（enabled: true、threshold_seconds: 2592000 即 30 天、target_timestamp 为空）。需明确其业务含义——是"首次访问后 30 天内可享优惠价"，还是其他规则？Agent 若引用倒计时营造紧迫感，必须与实际价格逻辑严格一致，不得虚构截止时间，否则构成虚假促销。
  10. 同一课程是否对应多位售前：若一门课由多人负责，弹码规则是什么（固定、轮询、按来源）？Agent 分流时需要遵循同一规则，否则会与现有分配习惯冲突。
  11. 企业微信的能力边界：售前承接渠道已升级为企业微信，但能力边界仍需确认。待明确：① 是否使用可带来源参数的「联系我」活码（决定 R19 能否自动归因）；② 企业微信客户联系 / 应用消息 API 是否对本项目开放（决定 R23 能否程序化推送）；③ 是否开通会话存档（既支撑 R18 售前语料沉淀，也涉及对用户的合规告知）；④ 企微后台能否提供分渠道的添加客户数与来源统计。
  12. 业绩归属的判定口径：归属规则已明确为"归属最近一次人工接触的售前"。待明确：① 时间窗——多久内的接触算"最近"（7 天 / 30 天 / 不限）？② 跨渠道判定——售前在微信接触、学员从其他渠道进入官网，是否同样认定？③ 纯自然流量成交（无任何人工接触记录）归谁——这是规则的空缺处，需销售负责人补口径；④ 业绩核算由谁执行、以哪份报表为准。口径未定前，R19 / R27 无法写验收标准。
  13. 非工作时段响应：扫码加好友后由谁接待？有无自动回复或值班安排？夜间与周末通常多久响应？
  14. 现有咨询入口数据：咨询按钮的点击量、扫码率、加好友后的转化情况——这是目前唯一可能拿到的近似基线，建议优先获取。
  15. 埋点与来源标识：能否在官网埋点，并在链接上区分自然流量与售前引流？现有是否已有统计工具（如百度统计、GA）可复用？
  16. AI 资源配额：openai.arborseek.com 是否为集团自建网关？可用模型、并发配额与成本预算是多少？
  17. 营销权限：Agent 是否被授权发放优惠券或折扣？折扣上限是多少？（影响 P2 需求可行性）
  18. 知识库维护方：课程介绍、师资、常见问题等内容由哪个团队负责提供与持续维护？
  19. B2B 分流方式：高校采购、企业合作类咨询转给谁？是否需要独立的留资表单？
  20. 各课程线的承接量上限：每条课程线（每位售前）单日可承接多少条线索？超出后的规则是什么（排队、兜底分配、还是降级呈现）？这是决定 Agent 是否需要对热门课程设置推荐限流的关键输入。
  21. 推荐权重的评审机制：已明确推荐权重暂不需要评审机制，因此不设评审流程与例会。仅保留推荐依据留痕（R25）与课程线线索分布月度同步作为运营透明度措施。若后续售前侧提出异议，再评估是否升级为评审机制。
  22. FDE 复用方式：是否确定以 FDE「统一知识助手」作为技术起点（推荐策略 B：搬内核、换外壳）？由哪个团队承担——官网前端、现有后台团队，还是原 FDE 开发者？
  23. 部署形态与用户体系对接：Agent 作为独立服务部署，还是并入 arboradmin.saikr.com 后台？官网登录态如何对接（SSO / 透传 token / 独立登录）？域名与跨域方案如何定？
  24. 会话内容落库的合规口径：为支撑线索归因（R19）与转人工摘要（R23），需保留会话内容；这与既有隐私设计（不记录问题全文）相反，需明确允许范围、保留期限与对用户的告知方式。

13. 下一步建议

  1. 把已落地的组织规则写成可执行口径（第 2.5 节）。人机分工（协同 C + 增强 B）与业绩归属（归属最近一次人工接触的售前）均已确认，下一步需与销售负责人补齐判定口径：时间窗、跨渠道范围、纯自然流量订单归属。口径明确前的其余设计工作不受影响，但 R19 / R27 的验收标准需待口径确定后补写。
  2. 把"入口归一"作为 MVP 第一条需求落地。不合并入口，Agent 一上线就会与现有"咨询"按钮打架，体验和口碑都会受损。
  3. 官网维护归属已确认为内部技术团队（见 3.3 节），下一步直接与该团队谈"三处授权"与排期：能否获得部署层脚本注入权限、后续是否有启用 CSP 的计划（当前未配置，已实测）、注入在其内部迭代中的优先级。需强调：这一步不构成其他工作的阻塞——Agent 可以先独立部署，优先服务售前内部，待授权到位后再沿 P1 → P2 → P3 逐步推向前台。
  4. 把技术诉求从"要代码"改为"要三处授权"。即部署层注入权限、现有"咨询"弹窗组件位置、课程—售前映射读取方式（见 3.3 节）。三处授权在跨团队协作中的可达成性，远高于源码移交。
  5. 把"课程内容文本化"列入 MVP 前置任务（见 3.4 节）。接口实测已确认售前二维码可直读、结构化字段齐备，真正的待办转移到"课程正文与 9 板块内容全部是图片"。建议双线推进：对 Top 20 课程请课程运营补录文本版要点（最准确）；其余课程用 OCR 批量转文本（FDE 已有该能力）。此事可与技术开发并行、不占排期，但直接决定知识库的覆盖质量与推荐理由的可信度。
  6. 确定 FDE「统一知识助手」的复用边界（第 3.2 节）。建议采用"搬内核、换外壳"（策略 B），并优先落一个只含"知识库问答 + 未命中转人工"的最小版本，用于在匿名自然流量下验证自助解决率。该版本不依赖问诊与推荐方案定稿，可与设计并行推进，也正好补上"无基线数据"这一短板。
  7. 继续澄清第 12 节其余各项（售前码字段的配置方式与兜底逻辑、课程接口的数据口径与倒计时规则、配套接口是否存在、售前人数与产能、语料可用性、企业微信的活码与 API 权限边界、现有咨询入口数据），这些决定 MVP 能否按期落地。
  8. 同步启动售前语料整理（低成本、高收益）。将售前历史沟通中的高频问题与顾虑整理成第一批知识库条目，可与技术开发并行推进。
  9. 组织规则已落地，可进入 PRD 撰写（阶段二）。人机分工、业绩归属、推荐权重三项确认后，方案的最大不确定性已由"组织能否接受"转为"能否按期实现"。建议先起草已确定部分——入口归一、问诊轮次与画像字段、登录态保持、知识库组织方式、埋点体系、EARS 条目；推荐权重与归属口径两处留占位待补，不阻塞其余内容。
  10. 据此产出 PRD，按 EARS 原则补充完整需求条目与验收标准；指标部分先写"采集口径"，目标值待分层基线出来后补齐。
  11. 建议先做 2 周小范围验证：在课程详情页上线最小可用版本，重点观察自然流量组的问诊完成率、推荐点击率与自助解决率，再决定是否全量铺开。
  12. 将本报告与后续 PRD 上传至项目资料库，形成团队统一上下文。
  13. 创建评审事项，邀请技术负责人、设计同学、测试同学参与，并将销售负责人与售前团队代表加为关注人——缺少销售侧的认可，这个项目很难在内部推得动。
