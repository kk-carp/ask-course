# 售前 Agent 项目 30 天开发能力训练计划

适用对象：有 Vue 开发经验，刚转向 Python 和 AI 应用开发的初级开发者。

训练项目：`p0-arborseek-agent` 天树探界售前咨询助手。

制定日期：2026 年 10 月 10 日。D1 表示实际开始训练的第一天，不绑定日历日期。

## 1 训练目标与执行方式

这 30 天的目标，是让你能独立解释一次咨询请求、完成一个有数据库与权限边界的小功能、定位三类故障，并用测试和评测判断一次改动是否值得交付。编码速度暂不作为考核指标。

计划以当前工作区代码为依据。项目已有较丰富的实现和测试，适合通过“阅读现有代码、独立实现小功能、验证自己的判断”训练。文档中的新增反馈功能、指标门槛和时间安排属于训练设计，不代表已经实现或已经达到。

### 时间预算

- 标准版：每周 5 次各 60 分钟，加 1 次 90 分钟验收，再加 1 次 30 分钟复盘。四周约 28 小时，D29 和 D30 各 60 分钟，总计约 30 小时。
- 每次 60 分钟按 10 分钟回顾、35 分钟独立操作、10 分钟验证、5 分钟记录分配。
- D6、D13、D20、D27 为 90 分钟验收；D7、D14、D21、D28 为 30 分钟复盘。
- 最小版：当天只有 30 分钟时，完成一个核心问题和一份证据；剩余任务顺延。必要时把计划拉长为 6 周，不压缩验收环节。
- 70/30 是工作与训练的参考比例，不是额外加班要求。忙碌时优先固定每周训练时段，交付任务仍按团队要求使用 AI。

### AI 使用规则

1. 阅读日：先自己画流程和写解释，至少投入 20 分钟，再请 AI 检查理解。不能把 AI 的解释直接当作阅读记录。
2. 实现日：允许查官方文档、搜索错误信息和查看现有基础设施；第一版新增业务代码与测试由你自己写，暂时关闭自动补全式代码生成。
3. 调试日：先留下复现步骤、两条假设和至少一条排除证据，再向 AI 求助。20 分钟毫无进展时可以请求提示，不必无限硬扛。
4. 评审日：AI 可以指出问题和提出问题。你先解释问题、自己修改，再验证。对建议逐条记录“接受或拒绝及原因”。
5. 每次标记协助等级：A0 独立完成；A1 查文档或获得提示；A2 获得 AI 生成的实现。A2 可以用于交付，但该训练任务需要隔天独立重做关键部分才能计为掌握。

### 工作区和训练环境

当前工作区已有大量未提交改动。开始练习前记录 `git status --short` 与当前提交，不直接切分支、重置文件或覆盖 `.env`。训练优先使用单独目录中的克隆或工作树；开始前明确训练基线是否包含未提交内容，避免只从 HEAD 创建练习环境后误以为它等于当前项目。

新练习分支可命名为 `codex/training-feedback`。使用独立本地数据库和虚构课程资料。故障注入以 pytest 的 monkeypatch、依赖替换和受控上游为主。现有业务数据、真实客户凭证及生产配置不用于练习。

## 2 从实际项目确定训练重点

### 你要读懂的真实调用链

前端入口：`frontend/src/main.js` 挂载组件，`frontend/src/Widget.vue` 管理对话交互，`frontend/src/api.js` 负责 HTTP 请求与 SSE 解析。

请求入口：`backend/main.py` 挂载路由和中间件；`backend/routes/ask.py` 接收 `/ask` 与 `/ask/stream`，准备身份、检查门禁、调度问答并输出响应。

业务编排：`backend/services/ask_orchestrator.py` 的 `iter_ask_turn` 和 `run_ask_turn` 统一处理问诊状态、意图、课程事实、正文问答和人工承接。并列问题由 `question_decomposition.py` 拆分。

正文问答：`backend/services/qa_service.py` 调用向量编码与 `backend/infra/retrieve.py` 的检索流程，再通过 `backend/infra/generate.py` 调用模型。检索涉及授权空间、课程范围、资料发布状态、混合检索和可配置重排。

结果保存与输出：站点问答通过 `widget_history.py` 认领请求并保存回答；`knowledge_guard.py` 在生成、落库及输出等阶段复核依据是否仍可发布。前端解析事件后更新消息、来源和课程卡片。

**当前项目使用自定义 Python 服务编排，未见 LangGraph 实现。** 不需要为了训练先迁移框架。也不是每次请求都执行 RAG 和 LLM：明确意图、课程事实、公开信息等路径可以提前返回。你需要解释“为什么选择这条路径”，而不只背一条线性的调用链。

### 优先掌握的六件事

- 阅读与解释：把一个函数讲成输入、输出、依赖、分支、副作用和失败行为。
- Python 与 FastAPI：类型、数据类、生成器、Pydantic 校验、依赖注入，以及同步调用在线程池执行的原因。
- 数据库：SQLAlchemy Session、事务、唯一约束、迁移、所有权校验和并发下的重复写入。
- Debug：沿请求编号、HTTP 状态、业务错误字段、堆栈和耗时指标缩小范围。
- 测试：区分纯规则、HTTP、数据库集成和真实模型评测，各自能证明什么。
- 交付判断：区分代码实现、测试通过、业务审核、官网联调和生产验收。

当前架构文档表明，真实官网身份联动、课程销售审核及生产闭环仍有待验收。训练时不要把已有适配器和测试当作这些事项已完成的证据。

## 4 第二周 独立实现会话反馈 API

周目标：独立实现一个范围可控的后端功能，练习接口契约、数据库、归属校验、异常与测试。先完成后端，前端只作为后续可选扩展。

### 训练需求

为官网咨询的一条**已完成回答**提交“有帮助或无帮助”的反馈，可附不超过 500 字的说明。此功能是本计划新增的练习需求，当前阅读范围内未发现现成反馈接口。

建议接口：`POST /widget/conversations/{conversation_id}/turns/{turn_request_id}/feedback`。

请求包含 `rating`，取值为 `helpful` 或 `unhelpful`；`comment` 可选；`request_id` 为本次反馈提交的 UUID。路径中的 `turn_request_id` 对应原问答请求编号，与反馈提交编号不同。第一版不支持修改、删除、后台统计或导出。

建议返回 `feedback_id`、`created_at` 和 `replayed`。首次成功为 201；相同反馈编号与规范化内容重试返回原记录，状态为 200；相同编号内容不同，或同一回答用另一个编号再次提交，返回 409。非法参数返回 422；无权访问、会话不存在、已删除或过期统一返回 404；本人可访问但回答尚未完成返回 409。数据库故障回滚后返回受控 503，不向客户端暴露底层连接信息。

### 数据和权限约束

- 建议新增反馈表，包含主键、会话 ID、原问答请求编号、反馈请求编号、评价、说明和创建时间。
- 至少为“会话加原问答请求编号”与“会话加反馈请求编号”建立唯一约束。单靠先查询再插入不能防止并发重复写入。
- 复用可信所有者解析与现有会话授权边界；写入期间锁定并复核会话有效性，确认对应已完成回答属于该会话。不能信任客户端传入的用户 ID。
- 与删除、过期清理及咨询关联行为一致：反馈随其目标会话管理，删除和清理不能留下失去归属的反馈。明确选择外键级联或现有清理流程，并测试实际路径。
- 评论只保存文字，不支持 HTML；不把评论送入回答模型。后续展示采用文本渲染，日志不记录评论正文或凭证。
- 单独记录保留期与隐私告知需要同步的地方。训练完成不等于已经获准部署收集真实用户反馈。

接口状态是本次练习的约定，实施时先写清楚，再围绕约定验证。已有会话权限、灰度和来源限制应保持生效。

## 5 第三周 学会用证据定位故障

周目标：至少独立定位三类故障。训练中先观察再改代码；故障被你“碰巧修好”但说不清原因，不计为完成。

每次使用同一份记录：现象 → 最小复现 → 两条候选原因 → 检查证据 → 排除项 → 根因 → 修复或隔离措施 → 回归检查。记录实际耗时与 AI 协助等级。

### D15 建立排查路线

- 操作：阅读 `backend/infra/request_context.py`、`backend/infra/metrics.py`、`backend/routes/metrics.py`、`backend/errors.py`，定位一次请求的编号和耗时。
- 交付物：排查清单，依次列浏览器请求、HTTP 状态、SSE 事件、业务错误字段、服务日志、分段耗时和数据库状态。
- 验收：能区分传输成功与业务成功，并说明“知识未命中”“上游失败”“系统未就绪”不该混为一类。

### D16 模型超时

- 注入方式：在测试边界替换模型 SDK 调用，使其产生受控超时。若直接替换 `generate_answer` 抛业务异常，只能证明下游处理，不能证明 SDK 异常转换正确。
- 定位入口：`backend/infra/generate.py`、`qa_service.py`、`ask_orchestrator.py` 和 `backend/routes/ask.py`。
- 交付物：失败测试与定位记录，注明异常在哪一层转为业务错误。
- 验收：故障没有被报告成普通知识未命中；不保存成功回答；流式错误被前端正确识别。分别核实普通与 SSE 路径的实际协议。

### D17 数据库不可用

- 注入方式：测试中替换 Session 创建或执行操作，产生受控数据库异常；有专用容器时可在训练实例停止该容器后观察健康检查。
- 定位入口：`db.py`、`backend/routes/health.py`、新增反馈服务与访问日志。
- 交付物：说明失败发生在启动、读数据还是提交事务，比较健康检查与业务接口的结果。
- 验收：不靠反复重启解释问题；反馈事务失败无脏记录，依赖恢复后可重试。模型超时和数据库故障有不同的证据链。

### D18 模型空响应与非法响应

- 注入方式：受控返回空 choices、空内容；另设一个结构不符合预期的响应。阅读 `generate.py` 的实际访问逻辑，先预测各自结果。
- 交付物：两类失败的差异记录及回归测试。
- 验收：能区分已处理的空回答与未被处理的数据结构异常。若发现真实缺陷，先形成复现，再在训练环境修复，不能用宽泛捕获吞掉所有异常。

### D19 删除和迟到响应

- 操作：阅读 `tests/test_widget_history.py`、`tests/test_response_concurrency.py` 及数据库集成测试，使用同步事件控制“开始生成、删除会话、完成生成”的顺序。
- 交付物：时序图和一条受控回归测试。不要仅靠随机 sleep 证明并发行为。
- 验收：删除后旧回答不能恢复记录；能解释输出、保存和前端显示分别有哪些保护。若本轮时间不足，先运行并解释现有案例，不新增复杂并发实现。

### D20 三类故障验收

- 操作：从超时、数据库故障、空响应中选择三个预设场景，打乱顺序后重新排查。可提前把注入脚本编号保存，减少按答案记忆。
- 交付物：三个定位报告，每份包括证据和一条回归检查。
- 验收：每个场景以 30 分钟定位为练习目标；超时也如实记录。看过答案后修复的场景标为 A1 或 A2，另日复测。必须解释根因，不以“重启后好了”结束。

### D21 故障复盘

- 操作：总结自己最常跳过的一步，例如未读完整堆栈、未检查实际请求字段或过早修改代码。
- 交付物：个人 Debug 清单，最多 8 条。
- 进入第四周条件：三个场景都有可重复复现和根因证据；仍依赖 AI 的场景安排重做。

## 6 第四周 用测试和评测证明改动有效

周目标：固定一组业务案例，建立修改前后的可比较记录，完成一次小范围改动，并说明收益与回归风险。

### D22 读懂已有评测工具

- 操作：阅读 `scripts/evaluate_dialogue.py`、`scripts/evaluate_pilot.py` 和 `data/eval/dialogue_smoke.jsonl`，识别每个脚本发送的通道和支持的字段。
- 交付物：工具边界说明。
- 验收：指出这两个脚本当前主要使用 `internal_tool` 通道，不能代替 `site_widget` 的真实身份、门禁、幂等和历史验收；后者需要相应 HTTP 与集成测试。

### D23 建立自己的 20 条评测集

- 操作：用虚构或获准使用的训练资料编写 20 条有明确预期的案例：课程事实 4 条、正文检索 4 条、推荐或问诊 4 条、人工承接 3 条、资料不足或冲突 3 条、并列问题 2 条。
- 交付物：`training_gold.jsonl` 与判分说明，每条注明依据、预期行为和禁止行为。另把权限和故障案例保留在确定性测试中。
- 验收：每条案例都能人工判断，不只判断回答是否“自然”。缺资料时允许合理拒答，不强行追求全部命中。

### D24 记录修改前基线

- 操作：固定代码提交、课程资料版本、模型标识、提示词、配置与并发条件，执行评测。真实模型运行前确认本地配置、可用服务与用量预算；无外部依赖时先完成受控版本并明确标记。
- 交付物：基线报告，记录案例 ID、回答、来源、判分、耗时与错误类型；可用时补充检索文档 ID、片段排名和 token 用量。
- 验收：区别“脚本已有字段”和“你补充的记录”。`evaluate_pilot.py` 已记录逐案秒数和回答，但不会自动给出完整检索轨迹、统一错误分类或 token 成本报表。

### D25 选择一个小改动并先写预测

- 操作：从自己观察到的问题中只选一个，例如课程事实路由遗漏、并列问题拆分边界或错误提示不清。尽量不在首轮改检索模型、并发架构或整个编排器。
- 交付物：改动方案，说明受影响案例、预计收益、可能退化的行为和回退方法；至少先得到一个能复现问题的测试。
- 验收：能解释为什么改动应放在这一层；其他人可依据方案判断它是否成功。

### D26 实现与对照评测

- 操作：完成改动，运行目标测试，用 D24 相同条件再跑评测；不在看到结果后偷偷修改金标来迎合输出。
- 交付物：前后差异与失败案例归因。
- 验收：目标问题改善，未新增严重错误。真实模型有波动时针对争议案例重复三次，逐次保留结果；受控 mock 的稳定性不能证明真实回答质量。

### D27 写交付说明

- 操作：运行与改动相关的回归检查，整理一个可供评审的 diff 与一页交付说明。发布、生产迁移和真实数据采集另按项目流程处理。
- 交付物：问题、改动、证据、风险、回退方法，以及未验证事项。
- 验收：另一位开发者只读说明即可复现检查；能说明单元测试通过为什么仍不代表课程审核、官网联调和上线签收。

### D28 复盘与小型口试

- 操作：请 AI 一次只问一个问题，覆盖 Python、HTTP、异常、数据库、并发、安全六个方面；回答后要求它指出对应代码证据。
- 交付物：六道题的个人回答与薄弱点。
- 验收：对不懂的问题明确说明，不背 AI 提供的答案；隔天能用自己的语言重新回答。

## 7 最后两天 综合考核与下一步

### D29 闭卷交付演练

60 分钟内完成三项：15 分钟讲解一条真实请求；25 分钟在反馈模块独立增加“说明去除首尾空白并验证边界”这类小需求及测试；20 分钟排查一条受控失败测试。若第二周已经实现该边界，改为一个同等规模、尚未实现的校验需求。

保留 diff、检查结果和排查记录。允许查文档，标记 A1；不接受 AI 生成实现作为本次独立能力证据。完成不了就记录具体卡点，不把超时等同于没有进步。

### D30 评估结果并安排后续 60 天

对六个维度分别评分：代码理解、API 实现、数据与权限、故障定位、测试评测、交付说明。统一尺度为：0 分没有证据；1 分依赖逐步指导；2 分查文档或少量提示可完成；3 分能独立完成并解释边界。

本轮建议通过条件：总分至少 12 分，数据与权限和故障定位各至少 2 分，且能解释自己新增的全部业务代码。它是个人训练门槛，不是行业招聘标准。没有通过时，针对最低两项再练两周，不重新从头刷课程。

后续安排：

- 第 31 至 60 天：每两周完成一个小型后端需求；重点补 PostgreSQL 查询与事务、异常分层、日志和部署排查。每周至少一次外部评审或 AI 追问。
- 第 61 至 90 天：在测试环境完成一次有备份、监控与回退记录的发布演练；深化一项真实业务评测。具备前述能力后，再按项目需要考虑新的 Agent 框架。
- 每月整理一个匿名化案例：一个独立功能、一个故障定位、一次有证据的质量改进。对外展示时不携带客户信息、内部课程原文或配置秘密。
- 评估成长环境时，关注能否接触代码评审、真实维护和工程指导。若工作长期集中于课件制作，可用这些案例了解岗位要求；不根据这份计划单独作离职决定。

## 8 验收指标与记录模板

### 四周应留下的能力证据

- 第一周：一张调用链图、三条分支预测、一次闭卷讲解。
- 第二周：一份设计、一个反馈 API、边界与事务测试、数据库验证记录。
- 第三周：三个可重复的故障报告，至少三次在 AI 给答案前写出定位证据。
- 第四周：20 条业务案例、一份基线、一次改动对照、一页交付说明。
- D30：六维评分、A0/A1/A2 记录，以及下个月只练哪两项的决定。

### 评测如何判分

功能正确率按“通过约定行为的案例数 ÷ 总案例数”记录，同时列每个类别的通过数，避免总体数字掩盖某类退化。不要用 `hit=true` 代替正确：并列问题中它可能只表示至少一项有依据。

严重错误单独计数，个人训练门槛设为零：跨归属读取或写入、已撤回依据继续输出、错误课程的购买入口或依据，以及未经证实的商业承诺。零例只说明本次测试集未发现，不能推导系统绝对安全。

检索质量对有标注文档的正文案例单独统计，例如前 k 条候选是否包含预期文档；事实短路和人工承接不放进这个分母。最终展示来源不等于完整候选集，需要在测试或受控日志中获取检索结果。

延迟记录样本数、中位数和 p95，并区分单条请求与多轮案例总耗时。20 条案例的 p95 只作初步观察；同条件下重复采样再讨论趋势。`benchmark_response_latency.py` 模拟上游等待，不代表线上耗时。没有测量前不设任意毫秒级目标。

同条件对照的建议准入条件：目标案例改善、原来通过的关键行为未退化、严重错误为零；耗时明显变差时先定位并说明代价。真实模型结果存在波动时保留重复结果，不挑最好的一次。

## 9 项目检查命令与使用边界

以下从训练项目根目录运行，并使用该项目的 Python 虚拟环境。先完成依赖安装；首次不要求把所有命令都运行一遍。

```powershell
# 第一天的轻量检查
python scripts/smoke_kernel.py
python -m pytest -q tests/test_intent_router.py tests/test_qa_retrieval.py

# 阅读或修改会话相关逻辑时
python -m pytest -q tests/test_widget_history.py

# 新增反馈测试后才执行，当前项目尚无这个测试文件
python -m pytest -q tests/test_widget_feedback.py

# 数据库集成，前提是 TEST_POSTGRES_URL 指向专用测试库
python -m pytest -q tests/integration

# 修改流式和前端行为时
npm test --prefix frontend
npm run build --prefix frontend
node --test tests/frontend_answer.test.cjs

# 模拟等待时间的调度基准
python scripts/benchmark_response_latency.py

# 已启动训练服务并准备相应资料后，才运行真实接口评测
python scripts/evaluate_dialogue.py --base-url http://127.0.0.1:8000
python scripts/evaluate_pilot.py --base-url http://127.0.0.1:8000 --dataset data/eval/training_gold.jsonl --output data/eval/training-baseline.json
```

`training_gold.jsonl` 是 D23 要新增的训练文件。改动后评测应指定另一个输出路径，例如 `training-after.json`，保留基线。`evaluate_pilot.py` 可调用真实服务和模型，不作为默认离线自检。

阶段验收时参照 `.github/workflows/checks.yml` 运行相关检查；涉及较广时再执行 `python -m ruff check backend scripts tests`、完整 pytest 与前端构建测试。记录通过、失败、跳过三种结果。没有设置 `TEST_POSTGRES_URL` 而跳过的集成测试不能计为通过。

当前 `pytest.ini` 的临时目录为 `.pytest-tmp-local`，与开发指南中部分文字不一致，执行时以实际配置为准；不要并行运行共用临时目录的多个 pytest 进程。发现文档与代码冲突时，把它作为阅读训练的一项证据，核实后再改文档。
